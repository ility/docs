# Code review

How review works in `ility/docs`: when to run one, how an agent
dispatches it, where the findings go, and how each one is resolved. It
follows [`ility/ility`'s `docs/standards/code-review.md`](https://github.com/ility/ility/blob/main/docs/standards/code-review.md),
trimmed to what this repo has (no plans, specs, or ADRs). For commit and PR
mechanics, see [`git.md`](git.md).

## When to review

- **As soon as you open a draft PR, unprompted.** An agent flips its own PR
  ready only after an independent review ([`git.md`](git.md#pull-requests)),
  so the review is part of opening the PR. Don't ask whether to run it or
  post it.
- **When stuck.** A reviewer without your session history spots framing
  you've locked into.

Don't skip a review because a change is "simple". Every merge here is
published to customers.

## Dispatching the reviewer

Use the `/code-review` skill, run by a reviewer with its own context and its
own checkout. In Claude Code, that is the Agent tool with
`isolation: "worktree"`, prompted to run `/code-review` against the range.
`/code-review` invoked inside the authoring session reviews the author's
checkout, so on its own it doesn't count.

Give the reviewer:

- The PR body.
- The standards the change touches: [`git.md`](git.md),
  [`markdown.md`](markdown.md), and the terminology and style in
  [`AGENTS.md`](../AGENTS.md).
- Where to check claims: the `ility/ility` code the page describes. A
  customer page that disagrees with the product is a correctness bug.
- The git range as `BASE..HEAD`, so it reads the real commits.

Don't give it your session transcript or your reasoning. A reviewer fed your
reasoning tends to agree with you.

## Posting the review

Post the review on the PR as a **formal review** (`gh pr review <N> --comment
--body-file <path>`), not a plain comment. GitHub allows only `--comment` on
your own PR, so put the verdict in the body:

```md
**Ready to merge?** With fixes.
```

Start the body with an attribution line, such as _Review generated by a
Claude Code reviewer subagent against `<base>..<head>`._ Strip local paths
and agent metadata before posting.

## The disposition framework

Every finding lands somewhere. None ends as a TODO in code or a silent
oversight.

| Finding                                   | Disposition                                  |
| ----------------------------------------- | -------------------------------------------- |
| Wrong claim, leaked secret, broken page   | **Fix in this PR.** No deferral.             |
| Small fix with no design decision         | **Fix in this PR** with a follow-up commit.  |
| Improvement outside this PR's scope       | **File a GitHub issue** and link it.         |
| Style or cosmetic                         | **Skip**, or defer to a sweep PR.            |

Post the disposition as a **follow-up comment**, not inside the review. It
pairs each finding with the fix commit SHA, the issue number, or a deferred
row:

```md
Deferred (#17) — out of scope. The navigation reshuffle is its own change.
```

The parenthetical is mandatory. A deferral with no issue is not a
disposition.

## Order of operations

1. Dispatch the reviewer.
2. Post the review **before** pushing fixes, so its line references match
   the head it reviewed.
3. Push one atomic commit per fix.
4. File an issue for every deferred finding.
5. Post the disposition comment.
6. Flip the PR ready once [`git.md`](git.md#pull-requests)'s four conditions
   hold.
